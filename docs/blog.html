architectural decisions for a daily bhopal news dashboard

December 2025 · 8 min read

why a structured architecture matters

The Bhopal/MP news dashboard started as a quick proof-of-concept pulling headlines from three free-tier APIs (NewsData.io, GNews.org, NewsAPI.org). Within weeks the system had to tolerate rate‑limit throttling, duplicate syndication, and a growing back‑catalog of articles. A clear architecture prevents the codebase from turning into a "spaghetti" of ad‑hoc queries and makes it possible to onboard new data sources without rewriting existing logic.

core principles

  • Provider‑agnostic ingest: each API is wrapped in a thin adapter that normalises headline, source, timestamp, and sector. New adapters can be added without touching the threading or beat logic.
  • Postgres‑backed persistence: all articles, threads, beats and metadata live in Neon Postgres under the bhopal schema. This gives us reliable querying, indexing, and historic analysis whereas JSON files quickly become unmanageable.
  • Scheduled cron ingest: a GitHub Actions workflow runs every 6 hours, calls each adapter, and calls create_event to thread or open a new chain. The 6 h interval balances freshness against free‑tier quota (≈100–200 req/day per provider).
  • Keyword‑driven threading: a new article is matched against open threads by (a) shared keywords, (b) token‑level Jaccard similarity on the headline, and (c) a minimum‑distinctive‑word gate. This avoids false merges when two unrelated stories share a common token such as "पुल" (bridge) vs "पुलिस" (police).
  • Beat collapsing: articles reporting the same development within ~36 h are collapsed into a single beat, recording the extra outlets as corroborating sources. Without this a single syndicated story would look like three independent developments.
  • Progress status inference: from the article snippet we infer STATUS_ONGOING, STATUS_DELAYED, STATUS_STALLED or STATUS_UNKNOWN using patterns such as "update", "reopened", "halted", or missing timestamps.

scaling to many APIs and data sources

When the system needs to ingest from dozens of regional feeds, local blogs, or social‑media monitors, the following extensions keep the architecture performant:

  1. Schema partitioning: each new data source gets its own table (or partitioned table) within the bhopal schema. Indexes on source, published_at, and thread_id are created per partition, so queries for a single source remain fast even with millions of rows.
  2. Async ingest workers: instead of a single cron job, dispatch each adapter to a lightweight worker (e.g. asyncio tasks or a Celery‑style queue). Workers respect per‑provider rate limits and back‑off on HTTP 429 responses.
  3. Feature‑flagged APIs: a small config table stores api_key, enabled, and daily_quota. The ingest scheduler reads this table so an admin can toggle a source on/off without a code change.
  4. deduplication at the DB level: a unique constraint on (source, external_id) prevents the same article from being inserted twice when multiple pipelines pick up the same syndicated feed.
  5. analytics & monitoring: a separate metrics schema tracks ingest latency, success/failure counts, and API quota usage. These metrics drive alerts (e.g. Slack webhook) when a provider approaches its free‑tier limit.

deployment considerations

The stack is already containerised for Render:

  • Backend: FastAPI + uv + SQLAlchemy async runs in python:3.13 with uv run uvicorn app.main:app --port $PORT. Environment variables API_URL and INGEST_SECRET are supplied as repo secrets.
  • Frontend: Next.js 16 + React 19 + Tailwind v4 built with Bun; the Dockerfile uses bun install && bun start and exposes the port Render assigns.
  • Render blueprint: render.yaml defines two services (api and web) in the ap-southeast-1 region, with a cron that triggers the GitHub Actions ingest.yml workflow every 6 hours.
  • CI / CD: on every push to main the CI pipeline runs uv run scripts/init_db.py to ensure the bhopal schema exists, and runs the test suite. Deploy happens automatically via Render’s GitHub integration.

Because all state lives in Postgres, a new deployment can simply point at the same database endpoint; no migration scripts are required beyond the idempotent init_db.py that creates tables and indexes if they are missing.

future‑proofing the story‑chain engine

The threading/beat logic currently lives in event_store.py and uses only Postgres columns. To support millions of articles we plan to:

  • Materialised views that pre‑compute per‑thread latest‑beat status, so the UI /chains endpoint is a simple SELECT against a view rather than a complex aggregation.
  • Graph‑based clustering (e.g. using Neo4j or Postgres’ pg_graphql) for exploratory “related stories” queries that go beyond linear chains.
  • incremental threading – when a new batch of articles arrives, only compare each new article against threads that were updated in the previous ingest window, reducing the pairwise comparison from O(n·m) to O(n·k) where k ≪ m.
